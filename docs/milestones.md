# Mikoshi v1 里程碑

本文把 [features.md](features.md) 的 v1 范围拆成 10 个里程碑（M0–M9）。每个里程碑结束都是一个检查点：你确认或调整之后，再开始下一个。

## 总览

| 里程碑 | 内容 | 结束时你能做什么 | 规模 | 写 .kdbx |
|---|---|---|---|---|
| M0 | keepass-rs 往返验证 | 拿到"keepass-rs 能不能用"的结论报告，决定走哪条路 | M | 只写测试库 |
| M1 | 工程骨架、安全基线、界面风格 | 启动一个空壳应用，看到用假数据做的界面样稿 | S | 否 |
| M2 | 打开、解锁、只读浏览 | 解锁真实的库，浏览全部内容 | M | 否 |
| M3 | 搜索、复制、TOTP、自动锁定 | 开着它日常查密码、复制、看验证码 | M | 否 |
| M4 | 托盘、全局热键、快速搜索框 | 在任何程序里按 `Ctrl+Alt+K` 搜到并复制密码 | M | 否 |
| M5 | 自动输入 | 在登录页按 `Ctrl+Alt+V` 自动填好账号密码 | L | 否 |
| M6 | 无损 KDBX 读写层，换掉 keepass-rs | 改用自己的读写层，保存测试库不丢任何内容，KeePassXC 能打开 | L | 只写测试库 |
| M7 | 条目编辑与保存 | 改条目并保存，KeePassXC 里能看到改动 | L | **是** |
| M8 | 删除与回收站、分组、附件、新建库、密码生成器 | v1 的 [必须] 功能全部可用 | M | 是 |
| M9 | 设置收尾、可选项、打包、v1 验收 | 拿到安装包，按 §7 验收通过 | M | 是 |

规模只表示相对大小（S < M < L），不是工期。

### 为什么先做只读、后做写入

- M1–M5 完全不写 `.kdbx`，从 M2 起你就可以拿**真实的库**试用，不用担心损坏数据
- 快速搜索和自动输入是 Mikoshi 和 KeePassXC 拉开差距的地方，先做能更早验证手感；这段时间编辑可以继续用 KeePassXC
- M0 发现 keepass-rs 写入会丢冷门数据；2026-11-18 决定在编辑之前插入 M6，自己写 KDBX 的读写层（原来的 M6–M8 顺延为 M7–M9，内容不变）

### 依赖

- M1 需要 M0 证明 keepass-rs 的**读取**可用
- M6 需要 M0 的测试库和往返测试工具
- M7 需要 M6 的读写层，以及 M3 的锁定流程
- M5 需要 M4：自动输入没匹配到条目时要打开快速搜索框
- 其余按顺序依赖前一个；M9 需要其他全部完成

## 检查点怎么走

每个里程碑结束时我会交付：

1. **演示步骤**：照着操作就能看到效果
2. **验收清单**：本文里每条验收的通过情况
3. **已知问题**：没做完的、和规格有出入的
4. **下一个里程碑的任务拆分**：细到可以直接开工

你确认后我打一个 git tag（`m0`、`m1`……）再开始下一个。范围有调整时，同步修改本文档和 features.md。

贯穿所有里程碑的规则：

- 涉及读写 `.kdbx` 的改动，都要跑往返测试
- 每个检查点都复查 §6 安全要求：前端只拿元数据；日志和错误信息里没有敏感内容
- 设置项随功能一起加，不攒到最后
- [可选] 功能默认不做，在对应里程碑的检查点由你决定（见文末"可选项"）

## M0 keepass-rs 往返验证

**目标**：写任何界面之前，先确认 keepass-rs 能读规格要求的全部格式，并且保存后不丢数据（features.md §2、§7）。

**内容**

- 建 Rust 工作区和核心库 crate（后面的应用直接复用），引入 `keepass` 0.17.x，开启 `save_kdbx4` 和 `totp`；给 dev 构建下的依赖开优化
- 测试库 `tests/fixtures/`：我先写一份制作清单，覆盖 §7 列出的全部组合。能用 `keepassxc-cli` 生成的我来做，必须用图形界面的（KeePass 2、KDBX 3.1、自定义图标等）由你做
- 读取测试：每个测试库都能用正确的密钥打开；密码错、密钥文件错、文件损坏三种情况能区分开
- 往返测试：打开 → 保存 → 重新打开，比对内容。**不能只用 keepass-rs 自己的数据模型比对**：它不认识的元素，两次读出来都看不到。要比对解密后的原始 XML，或者 `keepassxc-cli export` 导出的 XML
- 测量 Argon2 在 debug 和 release 构建下的解锁耗时

**交付**：`docs/m0-report.md`，逐项列出每种格式、每类数据是"完整保留 / 部分丢失 / 不支持"。

**验收**

- 往返测试一条命令就能跑完，输出比对结果
- 报告覆盖 §2 列出的全部待验证项

**需要你决定**

- 按清单制作测试库
- 如果有数据丢失：给上游提 PR、fork 后自己修，还是换方案

## M1 工程骨架、安全基线、界面风格

**目标**：先把工程结构和安全约束搭好，并在接入真实数据之前定下界面风格。

**内容**

- Tauri 2 + React + TypeScript + Vite + pnpm 工程，应用标识 `com.elmtran.mikoshi`，只配置 Windows
- 目录：`src/` 前端，`src-tauri/` 应用，核心库沿用 M0 的 crate（不依赖 Tauri，便于测试）
- 单实例：再次启动程序时把已有窗口切到前台（§3.6）
- 安全基线（§6）：release 构建关闭 DevTools；严格 CSP；不加载远程资源（字体等全部打包）；日志脱敏；错误类型里不带敏感内容
- 前后端接口约定：前端只拿条目元数据，复制、显示密码等操作都传条目 ID 给 Rust 端执行。写进 `docs/architecture.md`
- 配置文件读写（`%APPDATA%\com.elmtran.mikoshi\`）
- 代码检查和测试命令：ESLint、Prettier、clippy、rustfmt
- 界面样稿：用假数据做出主窗口三栏布局和快速搜索框，定下颜色、字体、间距等设计变量

**验收**

- `pnpm tauri dev` 能启动；再启动一次只会把已有窗口切到前台
- release 构建打不开 DevTools
- 样稿经你确认

**已确定**（2026-11-17）

- 界面风格：Windows 11 原生风格，加一条渐变强调色和少量交互动效。三套备选样稿当时放在 `design/mockups/`（M9 改版后删除，在 git 历史里）
- 界面语言：中文和英文都支持，设置里可选"跟随系统"
- 深色模式：支持，设置里可选跟随系统、浅色、深色

## M2 打开、解锁与只读浏览

**目标**：能解锁真实的库并浏览全部内容。这一步不写任何库文件。

**内容**

- 解锁界面：选择文件、最近文件列表、启动时自动选中上次用的库（§3.1）
- 三种解锁方式；全部密钥文件格式；KDBX 3.1、4.0、4.1；全部 KDF 和加密算法（§3.1）
- 解锁失败时分别提示：密码或密钥文件不对、文件损坏、格式不支持
- 三栏布局：分组树、条目列表（标题、用户名、URL、修改时间，可排序）、条目详情（§3.3）
- 详情显示全部标准字段、自定义字段、标签、附件列表和各项时间；过期条目明显标记；显示标准图标；回收站显示为普通分组
- 密码默认掩码，点击或 `Ctrl+H` 临时显示。只有这时才把这一个条目的值发给前端，隐藏后清掉（§6）
- 手动锁定（`Ctrl+L`）：Rust 端擦除解密数据，前端清空缓存。之后的各种自动锁定都走这条路径
- 键盘操作：方向键在分组树和列表里移动，`Tab` 在三栏之间切换

**验收**

- 每个测试库都能用对应的方式解锁；三种错误各自提示正确
- 打开你自己的库，内容和 KeePassXC 里看到的一致
- 在开发模式下检查前后端通信：没点"显示密码"之前，前端拿不到密码

**需要你决定**

- 标准图标用哪套：需要一套能按 KeePass 标准图标编号一一对应、授权合适的图标，我会给 2–3 个候选

**已确定**（2026-11-17）

- 标准图标：Mikoshi 自己画一套，和界面图标同一种线条风格（候选还有 KeePassXC 那套和 Fluent UI 图标）。预览见 `design/icons/index.html`
- 可选项：记住每个库上次用的密钥文件路径、显示自定义图标，两个都做
- 根分组列出回收站以外的全部条目（和 M1 样稿一致）；回收站排在最后

**进度**：已完成，检查点已确认（2026-11-17，tag `m2`）。"打开你自己的库"这条验收由你自行核对

## M3 搜索、复制、TOTP 与自动锁定

**目标**：可以开着它日常查密码。

**内容**

- 搜索（§3.4）：匹配标题、用户名、URL、备注、标签，不区分大小写，边输入边出结果，默认不搜回收站。匹配度排序也在这里做好，M4 的快速搜索框直接复用
- 复制（§3.5）：用户名、密码、URL、TOTP；快捷键 `Ctrl+F`、`Ctrl+B`、`Ctrl+C`、`Ctrl+U`、`Ctrl+T`
- 剪贴板：复制密码和 TOTP 时写入三个排除格式；到时间自动清空，但只在剪贴板里还是我们放的内容时才清；退出或锁定时立即清空
- TOTP（§3.7）：读取 `otp` 字段，显示验证码和剩余秒数；验证码在 Rust 端生成
- 自动锁定（§3.2）：全局空闲超时、Windows 锁屏、系统休眠或睡眠。有未保存修改时怎么处理放到 M7（那时才有编辑功能）
- 设置页第一版：空闲锁定时长、剪贴板清空时长

**验收**（含 §7 剪贴板部分）

- 复制密码后，Win+V 历史里看不到
- 到时间自动清空；清空前你自己又复制了别的内容，不会被误清
- TOTP 和 KeePassXC 显示的一致
- 空闲超时、`Win+L`、睡眠三种情况都会锁定

**已确定**（2026-11-17）

- 可选项全部做：字段前缀语法、模糊匹配和匹配度排序、最小化时锁定（默认关）、用默认浏览器打开网址（`Ctrl+Shift+U`，只限 http/https）、兼容 KeePass 2 原生 TOTP

**进度**：已完成，检查点已确认（2026-11-18，tag `m3`）

## M3 检查点

开发、测试都已完成（2026-11-18），测试中没有发现需要修复的问题。

做好的内容：

- **TOTP**：Rust 端自己实现（`totp.rs`），读 `otpauth://`、KeeOtp、KeePass 2 原生字段、老的 `TOTP Seed`；SHA-1/256/512、4–10 位、任意周期、Steam。M0 的 K3（缺 `digits` 给 8 位）、K4（小写密钥）在 Mikoshi 里不再出现。设置无法识别时显示"验证码设置无法识别"

- **自动锁定**：全局空闲（默认 5 分钟）、Win+L、睡眠/休眠、最小化（可选，默认关）
- **打开网址**：`Ctrl+Shift+U` 和网址旁的按钮，Rust 端校验只放行 http/https
- **设置**：设置面板加了"安全"一栏：空闲锁定时长、剪贴板清除时长、最小化时锁定、记住密钥文件
- 验证码超过 6 位时从中间分组显示（如 `1234 5678`）

## M6 无损 KDBX 读写层

**目标**：换掉 keepass-rs，自己实现 KDBX 的读写。保存时只改用户动过的地方，其余内容原样写回，从根上解决 M0 的 K 系列问题。M7 起的编辑和保存都建立在它上面。

**为什么**（2026-11-18 决定）：M0 发现的问题全在 keepass-rs 把 XML 转成自己的数据结构、保存时再重新生成 XML 这一步：它不认识或没照原样记下的内容就丢了，有的还会让整个库打不开。加密部分没有问题。上游从 0.17.0 之后没有新提交，别人也在踩同类问题（上游 #319、#377、#392）。继续用 KDBX 格式，是为了保留 KeePassXC 作兜底，以及其他设备上的客户端。比较过的其他方案：调用 KeePassXC/KeePass 2 的代码（C++/C#，太重）、换别的密码库格式、自己设计格式（都会失去 KeePass 生态）。

**内容**

- **外层容器**（单独的 crate `crates/kdbx`，不依赖应用的其他部分）：
  - 读：KDBX 3.1、4.0、4.1；KDF 用 AES-KDF、Argon2d、Argon2id；加密用 AES-256、ChaCha20、Twofish；gzip 压缩；4.x 的 HMAC 分块和内层头部（附件、受保护字段的流密钥），3.1 的哈希分块；受保护字段的内层流（Salsa20、ChaCha20）
  - 写：只写 KDBX 4.1（S1）；沿用原来的加密算法、KDF 参数和压缩设置；从 3.1 升级时，内层流换成 ChaCha20
  - 密钥：密码、5 种格式的密钥文件、两者组合；KeePass 1 的 `.kdb` 照旧拒绝
  - 错误要分清：密钥不对、文件损坏、格式不支持。3.1 解密后先核对开头的校验字节（K5）；任何畸形输入都返回错误，不 panic（K9）
  - 密码学原语全部用 RustCrypto 等成熟的 crate（aes、cbc、chacha20、salsa20、twofish、argon2、sha2、hmac），加上 flate2，不自己实现算法
- **XML 层**：
  - 解析成保留全部内容的文档树：元素顺序、属性、空白、不认识的元素都留着。K1、K2、K6、K7、K8 这一类问题自然消失
  - 在树上提供 Mikoshi 要用的视图：分组、条目、字段、标签、历史、附件引用、自定义图标、自动输入设置、库的元数据
  - 修改只动对应的节点，没碰过的原样写回
  - 受保护字段解密后的值放在会擦除的内存里，写回时重新用内层流加密
  - 时间戳两种写法都认：3.1 的 ISO 文本，4.x 的 Base64 秒数
- **替换**：`mikoshi-core` 改用新的读写层，M2–M5 的功能不变；keepass-rs 从依赖中去掉（TOTP 在 M3 已经自己实现）。`kdbx-compat` 改成以 `keepassxc-cli` 的结果为准，来检查新的读写层
- **测试**：
  - 读：全部测试库读出的内容和 `keepassxc-cli` 导出的 XML 逐项相同
  - 往返：打开 → 保存 → 重新打开，解开受保护字段后，内层 XML 除了 KDBX 4.1 必然要变的部分以外完全相同；`keepassxc-cli` 能打开并导出相同内容
  - 为 K1、K2、K5–K9 各准备一个测试库
  - 畸形输入：截断、翻转比特、随机数据，都不 panic（加一轮短时间的模糊测试）
  - 性能：解锁时间和 keepass-rs 相当

**验收**

- 全部测试库读取结果和 KeePassXC 一致；K 系列的测试库全部通过
- 往返保存后用 KeePassXC 打开，内容完整

- 用 `kdbx-compat check` 扫一遍你自己的库（只读，不写文件）通过

## M8 删除与回收站、分组、附件、新建库、密码生成器

**定下的做法**（2026-11-20 确认）
