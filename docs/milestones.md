# Mikoshi v1 里程碑

本文把 [features.md](features.md) 的 v1 范围拆成 9 个里程碑（M0–M8）。每个里程碑结束都是一个检查点：你确认或调整之后，再开始下一个。

## 总览

| 里程碑 | 内容 | 结束时你能做什么 | 规模 | 写 .kdbx |
|---|---|---|---|---|
| M0 | keepass-rs 往返验证 | 拿到"keepass-rs 能不能用"的结论报告，决定走哪条路 | M | 只写测试库 |
| M1 | 工程骨架、安全基线、界面风格 | 启动一个空壳应用，看到用假数据做的界面样稿 | S | 否 |
| M2 | 打开、解锁、只读浏览 | 解锁真实的库，浏览全部内容 | M | 否 |
| M3 | 搜索、复制、TOTP、自动锁定 | 开着它日常查密码、复制、看验证码 | M | 否 |
| M4 | 托盘、全局热键、快速搜索框 | 在任何程序里按 `Ctrl+Alt+K` 搜到并复制密码 | M | 否 |
| M5 | 自动输入 | 在登录页按 `Ctrl+Alt+V` 自动填好账号密码 | L | 否 |
| M6 | 条目编辑与保存 | 改条目并保存，KeePassXC 里能看到改动 | L | **是** |
| M7 | 删除与回收站、分组、附件、新建库、密码生成器 | v1 的 [必须] 功能全部可用 | M | 是 |
| M8 | 设置收尾、可选项、打包、v1 验收 | 拿到安装包，按 §7 验收通过 | M | 是 |

规模只表示相对大小（S < M < L），不是工期。

### 为什么先做只读、后做写入

- M1–M5 完全不写 `.kdbx`，从 M2 起你就可以拿**真实的库**试用，不用担心损坏数据
- 快速搜索和自动输入是 Mikoshi 和 KeePassXC 拉开差距的地方，先做能更早验证手感；这段时间编辑可以继续用 KeePassXC
- 如果 M0 发现 keepass-rs 写入会丢数据，修复工作（提 PR 或 fork）可以和 M1–M5 并行，只卡住 M6

如果你更想先把编辑做完，可以把 M6、M7 挪到 M4 前面，依赖关系允许。

### 依赖

- M1 需要 M0 证明 keepass-rs 的**读取**可用
- M6 需要 M0 证明**写入**可用（或者修复已完成），以及 M3 的锁定流程
- M5 需要 M4：自动输入没匹配到条目时要打开快速搜索框
- 其余按顺序依赖前一个；M8 需要其他全部完成

## 检查点怎么走

每个里程碑结束时我会交付：

1. **演示步骤**：照着操作就能看到效果
2. **验收清单**：本文里每条验收的通过情况
3. **已知问题**：没做完的、和规格有出入的
4. **下一个里程碑的任务拆分**：细到可以直接开工

你确认后我打一个 git tag（`m0`、`m1`……）再开始下一个。范围有调整时，同步修改本文档和 features.md。

贯穿所有里程碑的规则：

- 涉及读写 `.kdbx` 的改动，都要跑往返测试
- 每个检查点都复查 §6 安全要求：前端只拿元数据；日志和错误信息里没有敏感内容
- 设置项随功能一起加，不攒到最后
- [可选] 功能默认不做，在对应里程碑的检查点由你决定（见文末"可选项"）

## M0 keepass-rs 往返验证

**目标**：写任何界面之前，先确认 keepass-rs 能读规格要求的全部格式，并且保存后不丢数据（features.md §2、§7）。

**内容**

- 建 Rust 工作区和核心库 crate（后面的应用直接复用），引入 `keepass` 0.17.x，开启 `save_kdbx4` 和 `totp`；给 dev 构建下的依赖开优化
- 测试库 `tests/fixtures/`：我先写一份制作清单，覆盖 §7 列出的全部组合。能用 `keepassxc-cli` 生成的我来做，必须用图形界面的（KeePass 2、KDBX 3.1、自定义图标等）由你做
- 读取测试：每个测试库都能用正确的密钥打开；密码错、密钥文件错、文件损坏三种情况能区分开
- 往返测试：打开 → 保存 → 重新打开，比对内容。**不能只用 keepass-rs 自己的数据模型比对**：它不认识的元素，两次读出来都看不到。要比对解密后的原始 XML，或者 `keepassxc-cli export` 导出的 XML
- 测量 Argon2 在 debug 和 release 构建下的解锁耗时

**交付**：`docs/m0-report.md`，逐项列出每种格式、每类数据是"完整保留 / 部分丢失 / 不支持"。

**验收**

- 往返测试一条命令就能跑完，输出比对结果
- 报告覆盖 §2 列出的全部待验证项

**需要你决定**

- 按清单制作测试库
- 如果有数据丢失：给上游提 PR、fork 后自己修，还是换方案

## M1 工程骨架、安全基线、界面风格

**目标**：先把工程结构和安全约束搭好，并在接入真实数据之前定下界面风格。

**内容**

- Tauri 2 + React + TypeScript + Vite + pnpm 工程，应用标识 `com.elmtran.mikoshi`，只配置 Windows
- 目录：`src/` 前端，`src-tauri/` 应用，核心库沿用 M0 的 crate（不依赖 Tauri，便于测试）
- 单实例：再次启动程序时把已有窗口切到前台（§3.6）
- 安全基线（§6）：release 构建关闭 DevTools；严格 CSP；不加载远程资源（字体等全部打包）；日志脱敏；错误类型里不带敏感内容
- 前后端接口约定：前端只拿条目元数据，复制、显示密码等操作都传条目 ID 给 Rust 端执行。写进 `docs/architecture.md`
- 配置文件读写（`%APPDATA%\com.elmtran.mikoshi\`）
- 代码检查和测试命令：ESLint、Prettier、clippy、rustfmt
- 界面样稿：用假数据做出主窗口三栏布局和快速搜索框，定下颜色、字体、间距等设计变量

**验收**

- `pnpm tauri dev` 能启动；再启动一次只会把已有窗口切到前台
- release 构建打不开 DevTools
- 样稿经你确认

**已确定**（2026-11-17）

- 界面风格：Windows 11 原生风格，加一条渐变强调色和少量交互动效。三套备选样稿留在 `design/mockups/`
- 界面语言：中文和英文都支持，设置里可选"跟随系统"
- 深色模式：支持，设置里可选跟随系统、浅色、深色

## M2 打开、解锁与只读浏览

**目标**：能解锁真实的库并浏览全部内容。这一步不写任何库文件。

**内容**

- 解锁界面：选择文件、最近文件列表、启动时自动选中上次用的库（§3.1）
- 三种解锁方式；全部密钥文件格式；KDBX 3.1、4.0、4.1；全部 KDF 和加密算法（§3.1）
- 解锁失败时分别提示：密码或密钥文件不对、文件损坏、格式不支持
- 三栏布局：分组树、条目列表（标题、用户名、URL、修改时间，可排序）、条目详情（§3.3）
- 详情显示全部标准字段、自定义字段、标签、附件列表和各项时间；过期条目明显标记；显示标准图标；回收站显示为普通分组
- 密码默认掩码，点击或 `Ctrl+H` 临时显示。只有这时才把这一个条目的值发给前端，隐藏后清掉（§6）
- 手动锁定（`Ctrl+L`）：Rust 端擦除解密数据，前端清空缓存。之后的各种自动锁定都走这条路径
- 键盘操作：方向键在分组树和列表里移动，`Tab` 在三栏之间切换

**验收**

- 每个测试库都能用对应的方式解锁；三种错误各自提示正确
- 打开你自己的库，内容和 KeePassXC 里看到的一致
- 在开发模式下检查前后端通信：没点"显示密码"之前，前端拿不到密码

**需要你决定**

- 标准图标用哪套：需要一套能按 KeePass 标准图标编号一一对应、授权合适的图标，我会给 2–3 个候选

**已确定**（2026-11-17）

- 标准图标：Mikoshi 自己画一套，和界面图标同一种线条风格（候选还有 KeePassXC 那套和 Fluent UI 图标）。预览见 `design/icons/index.html`
- 可选项：记住每个库上次用的密钥文件路径、显示自定义图标，两个都做
- 根分组列出回收站以外的全部条目（和 M1 样稿一致）；回收站排在最后

**进度**：已完成，检查点已确认（2026-11-17，tag `m2`）。"打开你自己的库"这条验收由你自行核对

## M3 搜索、复制、TOTP 与自动锁定

**目标**：可以开着它日常查密码。

**内容**

- 搜索（§3.4）：匹配标题、用户名、URL、备注、标签，不区分大小写，边输入边出结果，默认不搜回收站。匹配度排序也在这里做好，M4 的快速搜索框直接复用
- 复制（§3.5）：用户名、密码、URL、TOTP；快捷键 `Ctrl+F`、`Ctrl+B`、`Ctrl+C`、`Ctrl+U`、`Ctrl+T`
- 剪贴板：复制密码和 TOTP 时写入三个排除格式；到时间自动清空，但只在剪贴板里还是我们放的内容时才清；退出或锁定时立即清空
- TOTP（§3.7）：读取 `otp` 字段，显示验证码和剩余秒数；验证码在 Rust 端生成
- 自动锁定（§3.2）：全局空闲超时、Windows 锁屏、系统休眠或睡眠。有未保存修改时怎么处理放到 M6（那时才有编辑功能）
- 设置页第一版：空闲锁定时长、剪贴板清空时长

**验收**（含 §7 剪贴板部分）

- 复制密码后，Win+V 历史里看不到
- 到时间自动清空；清空前你自己又复制了别的内容，不会被误清
- TOTP 和 KeePassXC 显示的一致
- 空闲超时、`Win+L`、睡眠三种情况都会锁定

## M4 托盘、全局热键与快速搜索框

**目标**：不打开主窗口，在任何程序里都能快速拿到密码（§3.6）。

**内容**

- 托盘图标，菜单项：显示主窗口、锁定/解锁、快速搜索、退出；关闭主窗口时只隐藏到托盘
- 全局热键：`Ctrl+Alt+K` 呼出快速搜索框；热键可在设置里修改，注册失败时提示
- 快速搜索框：无边框、居中、置顶、不在任务栏显示；库未解锁时先输入主密码；方向键选择；`Enter` 复制密码并隐藏，`Ctrl+B` 复制用户名，`Ctrl+T` 复制 TOTP；`Esc` 或失去焦点时隐藏
- 呼出时记下之前的前台窗口，留给 M5 的 `Ctrl+Enter` 使用

**验收**

- 在浏览器、记事本等程序里按 `Ctrl+Alt+K`，搜索、复制、隐藏都正常，隐藏后焦点回到原来的窗口
- 库已锁定时呼出，先解锁再进入搜索
- 用别的程序占住热键，Mikoshi 会提示
- 关闭主窗口后程序仍在托盘

## M5 自动输入

**目标**：完成自动输入的全部 [必须] 功能（§3.10）。做完这一步，只读版本的核心卖点就齐了。

**内容**

- 触发入口：全局 `Ctrl+Alt+V`、主窗口 `Ctrl+Shift+V`、快速搜索框 `Ctrl+Enter`
- 匹配：窗口关联（支持 `*` 通配符）；没有窗口关联的条目按窗口标题是否包含条目标题；匹配到多个时弹出选择框，一个都没有时打开快速搜索框
- 序列：默认序列、条目和窗口关联的自定义序列、§3.10 列出的全部占位符和转义字符
- 模拟输入：用 `SendInput`，普通字符用 `KEYEVENTF_UNICODE`，功能键用虚拟键码；等触发热键的修饰键松开再开始；按键间隔可设置；输入前确认前台窗口没变
- 中文输入法：输入前切到英文模式或关闭输入法，输完恢复。微软拼音和搜狗都要实测
- UIPI：目标窗口以管理员身份运行时，检测出来并提示用户

**验收**（§7）

- Edge、Chrome 的登录页，记事本
- 开着微软拼音、搜狗输入法的场景
- 以管理员身份运行的窗口能看到提示

**风险**：输入法的处理没有标准做法，可能要试几种方案。检查点会说明最终用了哪种、在哪些场景下验证过。如果你担心这块，可以在 M1 之后先做一个输入法小实验，提前暴露问题。

## M6 条目编辑与保存

**目标**：能安全地修改并保存库。**从这里开始 Mikoshi 会写 `.kdbx`，检查点通过之前请只用库的副本测试。**

**内容**

- 条目新增、编辑（§3.8）：标准字段；自定义字段增删改，每个可单独设为受保护；`Ctrl+N`、`Ctrl+E`/`Enter`
- 进入编辑时才把这个条目的明文发给前端，编辑结束后清掉（§6）
- 设置 TOTP：粘贴 `otpauth://` URI，或者手动填密钥（§3.7）
- 历史记录：编辑前自动保存旧版本，遵守库里的历史条数上限；能查看历史版本并恢复
- 保存：
  - 先写临时文件，再原子替换原文件；保存前保留 `*.kdbx.bak`（可关）
  - 保存前对比打开时记下的修改时间和哈希，被外部改过就提示：重新加载、强制覆盖或取消
  - 沿用原来的加密算法、KDF 参数和压缩设置
  - KDBX 3.1 的库第一次保存前，提示会升级为 KDBX 4
- 标题栏显示是否有未保存的修改，`Ctrl+S` 保存
- 锁定时有未保存的修改：按设置自动保存或提示（补完 §3.2）
- 往返测试增加"修改后保存"的用例：用 Mikoshi 的代码改库，再用 `keepassxc-cli` 读出来比对

**验收**

## M7 删除与回收站、分组、附件、新建库、密码生成器

**目标**：v1 的 [必须] 功能全部完成。

**内容**

- 删除（§3.8）：条目和分组删除后进回收站（`Delete`）；在回收站里再删是永久删除，要二次确认；可以清空回收站
- 分组：新增、重命名、移动；条目在分组之间移动（拖拽和菜单都支持）
- 附件：导出到文件
- 新建库（§3.1、§3.8）：设主密码，可以再加密钥文件；KDBX 4 + Argon2id，KDF 参数按本机性能校准到解锁约 1 秒
- 密码生成器（§3.9）：长度、大小写、数字、符号可设置，可排除易混淆字符；用系统 CSPRNG；zxcvbn 强度估算；编辑时可填入密码栏，也能单独打开（`Ctrl+G`）只复制结果；记住上次的参数

**验收**

- 新建的库能在 KeePassXC 里打开（有条件的话再用 KeePassDX 试一下）
- 删除、从回收站移回、永久删除、清空回收站都正常
- 生成器各项设置都生效，强度显示合理

**需要你决定**

- 新建库默认用 AES-256 还是 ChaCha20。我建议 AES-256：有 CPU 硬件加速，也是 KeePass 系一贯的默认值
